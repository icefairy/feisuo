# 把 AI 编程 Agent 接进飞书：我造了一个多会话网关「飞梭」

> 项目已开源：https://github.com/icefairy/feisuo

## 一、起因：AI 能写代码了，但我不想一直坐在终端前

过去大半年，我的开发流程逐渐变成了这样：在终端里跑一个 AI 编程 CLI，让它读仓库、改文件、跑测试，我盯着它输出，时不时补一句“这个方向不对”。

效率确实高，但有个问题：**我被绑在电脑前了**。

很多需求是在通勤路上、开会间隙、躺床上刷手机时冒出来的。等我回到电脑前，灵感已经凉了。我也试过用手机 SSH 连回服务器，体验只能说勉强能用——小屏幕看长输出、打字纠错、切窗口，全是折磨。

我想要的其实很简单：

- 在飞书里像跟同事聊天一样派活；
- 任务在服务器上真实执行，能读写代码、跑命令；
- 执行过程能实时看到，不用等结束才一股脑吐出来；
- 不同项目的上下文互相隔离，别串味；
- 服务器重启后，会话和历史还在。

现有的方案要么只能接大模型 API（干不了活），要么是单会话、无隔离、无持久化。于是我干脆自己写了一个，取名**飞梭（feisuo）**——取“穿梭往来”的意思。

---

## 二、它是什么

一句话：**飞梭是一个飞书机器人网关，把飞书消息路由给每个会话独立常驻的 CLI Agent 进程，并把流式输出实时回传到飞书。**

```
飞书消息 ──► feisuo ──► 引擎 CLI（pi / codebuddy）──► LLM
     ▲                          │
     └──────── 流式回传 ◄────────┘
```

它不直接调模型 API。真正干活的是本机的 AI 编程 CLI（目前支持 `pi` 和腾讯的 `codebuddy`），飞梭负责的是**会话管理、消息路由、流式回传、权限与生命周期**这些“网关该干的事”。

这样做的好处是：Agent 的能力（读写文件、执行命令、跑测试、调工具）全部原样保留，飞梭不用重复造轮子；而且换模型、换引擎都不用改网关代码。

功能概览：

- 多会话并行，每个会话一个独立常驻进程，上下文完全隔离；
- 流式回传，Agent 的输出逐段实时可见；
- 持久会话，飞梭重启后自动恢复（包括对话历史）；
- 会话角色、按会话绑定工作目录；
- 会话间协作：Agent 可以把任务转给另一个会话；
- 飞书用户白名单认证；
- 终端 `attach`，可以像 tmux 一样挂到任意会话旁观/接管；
- 双引擎热切换，模型热切换；
- 闲置自动回收，不用的进程一小时后自动停掉。

下面挑几个我觉得最有意思的设计聊聊。

---

## 三、设计一：一个会话 = 一个进程 + 一条队列

很多“聊天机器人”是单会话的：所有消息进同一个上下文，聊到后面模型自己都晕。飞梭从一开始就按**多会话**设计：

```
会话 A ── 队列A ── 常驻进程 A（独立上下文）
会话 B ── 队列B ── 常驻进程 B（独立上下文）
会话 C ── 队列C ── 常驻进程 C（独立上下文）
```

每个会话首次收到消息时才拉起进程，之后所有消息通过 stdin 发 JSON 命令，流式事件从 stdout 读。会话之间互不干扰，A 在重构代码，B 在查日志，C 在写文档，可以同时跑。

队列还解决了另一个问题：**任务执行中又来了新消息怎么办？**

- 如果是飞书用户直接发的，飞梭会把它当作“纠正/补充”，用 steer 打断当前任务并立即处理，不用等它跑完；
- 如果是其他会话转发的（bridge）或终端 attach 发来的，就老老实实排队，不打断。

这个区分很重要——人类急着纠错，机器之间的协作则应该守规矩。

**持久化**是另一个关键点。CLI 进程本身就用固定的 `--session-id feisuo-<会话名>` 启动，对话历史由 CLI 自己落盘。所以飞梭重启、进程被杀、甚至闲置回收，都不影响上下文——下次消息拉起进程，接着聊。

---

## 四、设计二：流式回传，但不能把飞书刷爆

直接调 API 流式输出很简单，难的是**在 IM 里优雅地流式**。

飞书的消息编辑有次数上限（单条 20 次左右）。如果每个 token 都编辑一次，几秒钟就把额度烧完了；如果只在结束时发一条，又失去了“实时看到进展”的意义。

飞梭的做法是：

- **1.5 秒编辑间隔**，把增量合并后再刷；
- **单条消息编辑预算 15 次**，留余量给上限；
- **预算用完就“翻页”**：结束当前消息，开一条新消息继续写，形成滚动效果；
- **自适应退避**：遇到限流自动拉长间隔，再不行就降级为分段发送。

最终效果是：你在飞书里看到的是一条不断生长的消息，长任务写满了就自动接到下一条，既实时又不炸屏。

## 五、设计三：双引擎抽象，凭据一律复用

飞梭抽象了一层统一的 `Engine` 接口：

```go
type Engine interface {
    Execute(ctx, session, prompt, onChunk, onDone)
    ExecuteSteer(...)
    Steer(session, msg) error
    Abort(session) error
    Reset(session) error
    Kill(session)
    Close()
    ...
}
```

`pi` 和 `codebuddy` 各实现一份，上层逻辑完全不用关心底下是谁。带来两个直接好处：

1. **`/SWITCH pi` / `/SWITCH codebuddy` 运行时热切换**，立即生效并持久化；
2. **`/MODEL deepseek-v4.1-flash` 全局切模型**，同样立即生效、重启保留。

切换引擎或模型会重建进程，但会话 ID 不变，上下文照常恢复。你可以在飞书里一句话把“翻译会话”从 A 模型换到 B 模型，历史还在。

另一个刻意为之的决定是：**飞梭不保存任何凭据**。

- `pi` 引擎复用 `pi auth` / `models.json` 的配置；
- `codebuddy` 引擎复用本机登录态。

yaml 里的 `model` / `api_key` 全是可选项，留空就用引擎自己的配置。理由很朴素：凭据只应该存在一个地方，多一处就多一份泄漏面，也多一份“为什么两处配置不一致”的排障成本。

## 六、设计四：会话之间可以互相派活

单会话再强，也只是一个上下文。飞梭做了个很小的协议：Agent 在回复里输出

```xml
<bridge to="运维">帮我查一下昨天这个服务的错误日志</bridge>
```

飞梭就会解析这个标记，把内容转发给目标会话，对方的回复再流式回传给同一个用户。支持链式 A → B → C，最大深度 5，自转发忽略，用来防环。

实际用起来很像一个小团队：主会话负责拆解和汇总，专业会话负责查日志、写前端、做代码审查。每个会话还可以配置自己的角色（system prompt），比如“你是资深代码审查员，只关注正确性、边界条件和可维护性”。

## 七、踩过的坑

这部分可能比功能本身更有意思。

### 1. 权限审批把会话挂死了

`codebuddy` 默认会在执行敏感操作时弹权限确认。在终端里没问题，但飞梭是无人值守的——弹窗没人点，会话就永远卡在那里。

解决办法是启动时加 `-y` 和 `--permission-mode bypassPermissions`，再配合环境变量 `CODEBUDDY_IS_SANDBOX=1` 实现完全放行。

但这里还埋着一个更隐蔽的坑：一开始子进程的 `cmd.Env` 只设置了 API key，结果 `PATH`、`HOME` 全丢了，CLI 找不到自己的凭据目录，表现就是莫名其妙的启动失败。后来改成**基于 `os.Environ()` 追加**才正常。给子进程传环境变量时，永远别忘了继承父进程环境。

### 2. 飞书 WebSocket 半开僵死

飞书的机器人走 WebSocket 长连接，不需要公网 IP，很适合家用服务器。但长连接会“假活”：TCP 层看起来还连着，实际上已经收不到任何事件了，日志一片安静，消息却石沉大海。

最早的方案是“超过 N 分钟没收到事件就判定僵死”，结果把长任务误杀了——Agent 跑一个 20 分钟的重构，这期间当然没有入站消息。

现在的方案改成**只看连接状态**：

- 连接处于已连接状态 → 永远不判死，长任务期间没消息是正常的；
- 连接断开且超过阈值（默认 600 秒）还没恢复 → 判定僵死，进程优雅退出，交给 supervisor 重启重建。

看门狗每 30 秒检查一次。这个改动之后，再也没有误杀过长任务，也没再出现“机器人装死”。

### 3. 闲置进程吃内存

每个会话一个常驻 CLI 进程，上下文隔离的代价就是内存。十几个会话放那儿不用，内存就悄悄涨上去了。

于是加了闲置回收：`sessions.idle_timeout` 默认 3600 秒，超过一小时没有活动的会话，自动 `Kill` 掉它的常驻进程。因为会话 ID 是固定的，下次发消息会自动重启并恢复上下文，用户完全无感。

注意回收条件卡得很严：必须是 `idle/done/error` 状态、队列为空、且确实超过阈值。正在跑的任务、排队中的消息，一律不动。

### 4. 长任务超时

默认单任务超时 1800 秒。但有些任务就是会跑很久，超时一刀切会很难受。所以配置里显式写 `timeout: 0` 就是不设超时，把“要不要中断”的决定权交回给人（`/STOP`）。

## 八、怎么用

配置只有三件事：飞书应用凭证、选引擎、选数据目录。

```yaml
engine: "codebuddy"   # pi | codebuddy

feishu:
  app_id: "cli_xxx"
  app_secret: "xxx"
  bot_name: "飞梭"
  ws_url: "wss://open.feishu.cn/ws/v1/ws/"
  ws_health_timeout: 600

sessions:
  data_dir: "~/.feisuo/sessions"
  default_name: "main"
  idle_timeout: 3600
```

编译就是一个普通的 Go 项目：

```bash
go build -o feisuo .
./feisuo feisuo.yaml
```

然后在飞书里：

| 输入 | 效果 |
|---|---|
| `你好` | 发给当前会话 |
| `/TO 分析` | 切换到“分析”会话 |
| `/NEW repo --dir /data/codes/foo` | 新建会话并绑定项目目录 |
| `/CD repo /data/codes/foo` | 给已有会话换工作目录 |
| `/ROLE 排障 --role "资深 SRE"` | 设置会话角色 |
| `/STOP 分析` | 打断当前任务，不销毁会话 |
| `/RESET 分析` | 清空上下文 |
| `/COMPACT 分析` | 压缩上下文，省 token（pi） |
| `/SWITCH pi` | 热切换引擎 |
| `/MODEL xxx` | 热切换模型 |
| `/STATUS` | 看所有会话状态 |
| `/KILL 分析` | 杀掉进程（下次消息自动复活） |

工作目录这个功能我用得最多：给每个会话绑定一个仓库，Agent 的文件读写、git 操作、shell 命令全在那个目录里跑。相当于在飞书里开了 N 个互相隔离的“开发工作台”。

另外还有个终端侧的 `attach`：

```bash
feisuo attach ice
```

可以直接在终端里实时旁观某个会话的收发，也能手动输入接管。配合 tmux 分屏，可以同时盯好几个会话——飞书和终端操作的是同一个会话，两边实时同步。

部署上就是一个单二进制 + 一个 yaml，用 supervisor 或 NSSM 托管即可，Windows 也能原生跑（attach 通道从 Unix socket 换成本地 TCP）。

## 九、适合谁，不适合谁

**适合：**

- 有自己服务器、平时用 AI 编程 CLI 干活的开发者；
- 经常在外面，想用手机派活/看进展的人；
- 同时维护多个项目，需要上下文隔离的人；
- 想给团队搭一个内部 AI 助手机器人的团队。

**不太适合：**

- 想要开箱即用 SaaS 的人——这个项目需要你自己部署、自己配飞书应用；
- 只需要聊天问答的人——直接调 API 更简单；
- 对安全隔离要求极高的场景——飞梭的 codebuddy 引擎是权限全通过模式，本质上是把本机执行权限交给了 Agent，请只在可信环境使用。
